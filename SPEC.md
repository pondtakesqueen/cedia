# cedia spec

cedia is a personal coding harness written from scratch in TypeScript on Bun. It replaces Claude Code and Codex for one developer's daily work. The goal is a harness the user can trust and afford: every "done" is backed by evidence the harness recorded, and the prompt cache hit rate matches the DeepSeek harness. Progress is measured by an eval suite run against pi, Claude Code and Codex on the same tasks.

The full plan, with the comparison against other harnesses and the review it went through, is the "แผนสร้าง cedia v1" doc (rev 17, 2026-10-21). Research findings and source paths are in `research/NOTES.md`.

## Decisions

| Topic | Decision |
|---|---|
| Language, runtime | TypeScript on Bun |
| Shape | Own core, written here. Libraries as dependencies where they do not touch the core: Ink for the TUI, `@anthropic-ai/sandbox-runtime` for the sandbox. Not a fork: the pi-era cedia ran into pi core limits (paste expansion before hooks, provider layer) that needed a fork, and the core is where cedia differs. |
| Plan and thinking | Claude top-tier through an API key (Anthropic Messages) |
| Writing code | DeepSeek V4.1 Flash through OpenCode Go (ZDR); beam-free for volume work while it is free. When the Go quota runs out, Haiku 5.5 on the Claude API picks the task up in a new session: off the Go plan, not trained on, and as good on the hard evals for less. DeepSeek's own API (`deepseek-api`) counts as `trains`, so under `no-training` it runs only in public repos. The same model through OpenRouter (`deepseek-or`, `OPENROUTER_API_KEY`) is pinned to endpoints that keep no prompts (Cloudflare's, then DeepInfra's fp8 only when Cloudflare refuses a request; `provider: {order: ["cloudflare", "deepinfra/fp8"], allow_fallbacks: false, zdr: true, data_collection: "deny"}` in every request), so it counts as `zdr`. Left to OpenRouter's routing a session moved between endpoints, each with its own cache, and read 24.5% from cache; pinned to Cloudflare, 91.8%, and to DeepInfra fp8, 95.7%. With Cloudflare alone, a 429 from its shared upstream pool ended a split-plan run part way. It is its own eval arm, not the Go one. A model can carry lines of its own after the base system prompt (`ModelSpec.prompt`, `systemFor` in `core/prompts.ts`), fixed per model so a session's prefix never changes; DeepSeek Flash has three, from where it spent turns that Claude Code did not on the same task: test files of its own, a check rerun in a loop, one shell step per call |
| Muse Spark | Only on repos marked public: the Contributor tier trains on prompts and completions |
| Wire formats | Anthropic Messages, Chat Completions, OpenAI Responses |
| Auth | API keys only, from the environment (`CEDIA_ANTHROPIC_API_KEY` stands in for `ANTHROPIC_API_KEY`, which Claude Code cloud sessions drop), then on macOS from the Keychain (a generic password with service `cedia` and the variable's name as account, so the CLI and the desktop share one store; `CEDIA_KEYCHAIN=off` skips it), or added by an egress proxy (cloud network secrets). The secret-path guard denies bash calls that read the Keychain (`security find-generic-password` and the like). No Claude.ai or Cursor OAuth, no request that impersonates another client. A Claude subscription is used only by running the user's own Claude Code CLI as the plan or review step (`claude-code[:<model>][@<effort>]`); cedia never reads or sends its credentials, and strips API keys from its environment so it bills the subscription |
| Roles | One run is plan > code > review > one fix round. With a plan role, the writer's model first reads the message alone (a `triage` session with no tools, `TRIAGE_SYSTEM` in `core/roles.ts`) and answers PLAN or DIRECT: a greeting, a question, a request to run or explain something, or a change already spelled out goes straight to the writer, since planning "hi" took 6 s in Claude Code and pulled its memory into the reply; anything else, anything unsure and any unreadable answer is planned (`--plan-when auto|always|never` or `planWhen` in settings, default auto, and `/plan` or `/quick` in the TUI for one prompt; the triage model is `--triage`/`roles.triage`, default the code model, so it works with any writer; an answer to the writer's question is always planned). A change of at most 40 added and removed lines to a message the triage sent straight to the writer is not reviewed either: on the eval's small tasks the review found nothing in 8 of 8 runs and was most of each run's time (`SMALL_CHANGE_LINES` in `core/trust/review.ts`). A cedia model for plan or review takes its own effort as `<ref>@<effort>`, as `claude-code[:<model>][@<effort>]` does. `--plan`, `-m` (code) and `--review`, or `roles` in `~/.cedia/settings.json` (a repo cannot set them); each is a catalog model or, for plan and review, `claude-code[:<model>][@<effort>]` (opus at medium by default: on agentic repo work Opus medium scored above Sonnet at every effort and above Opus high or max, `research/NOTES.md`), or `none`. The code role always runs in cedia, where writes meet the policy, sandbox and done gate. Plan and review are read-only: in cedia, read and bash under a read-only policy plus the declared checks; in Claude Code, `--tools` and `--permission-mode dontAsk` with only Read, Grep, Glob, read-only git and the checks allowed, and `--restricted --strict-mcp-config --disable-slash-commands` so the repository under review runs no hook, MCP server or command through it (no settings file is read; the login is kept). With `--spawn worktree` (and a mode that writes), the planner may split the work: it ends its plan with 2 to 4 `<part files="…" model="…">brief</part>` blocks for parts that change different files and can be done and checked from a brief alone (the goal, the files with lines and signatures, what to change, the check), leaving parts that need judgment across the code, or depend on each other, to the writer. When the parts are usable (no file in two, each with files and a brief), cedia hands each to a `work` sub-thread from its brief word for word before the writer starts, all at once, each in a worktree of its own (outside git, one after another in place). With spawn on but no worktrees the planner is not asked to split: the parts would run one after another, each reading its part again, and on the 2026-10-24 real tasks they took 121 s of 683 s per task before the writer, which then read and checked it all anyway (writer-spawned work sub-threads in place took 386 to 549 s against 293 to 319 s with spawn off, 2026-10-22). A part runs on the code model, or on one of `--workers` (`roles.workers`, comma-separated refs) when the planner names it, so it can pick the cheapest model that will get each part right. The writer then gets the plan and the parts' reports, does the rest and runs the checks; what the parts changed counts as written before its session, so the done gate wants a check after it (`core/roles.ts`). A part itself is not held to the run's checks: they cover the whole task and can fail until the other parts and the writer are done, and 5 of 6 parts on 2026-10-24 were sent back by the done gate for a suite they could not pass. Deciding what to delegate, and to which model, is left to the planner, as in Anthropic's orchestrator-workers pattern and pstack: no DeepSeek run ever delegated on its own, and a writer passing the plan's briefs on would cost a turn and could lose their detail. Under `zdr` a step does not go to Claude Code. A Claude Code step's session and notional cost stay in Claude Code; consumer plans may train on it unless "Help improve Claude" is off |
| Sandbox | `@anthropic-ai/sandbox-runtime` (bubblewrap on Linux, sandbox-exec on macOS) around every bash call: writes only in the working directory and temp dir, no reads of the credential stores (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/.netrc`, `~/.docker/config.json`, `~/.git-credentials`, `~/.npmrc`, `~/.pypirc`, `~/.kube/config`, cedia's home), network only to package registries plus `--allow-domain`/user settings. `--sandbox auto` (default) falls back to unsandboxed with a stderr note; `on` requires it. Bash never inherits keys, tokens or `CEDIA_*` env. Edit and write never touch `.git/` or `.cedia/` |
| Permission | cedia never stops to ask for permission: a denied call returns its reason to the model and the run goes on, so it can be left alone. Modes `auto` (default: `workspace` when the sandbox is on, `read-only` when it is off), `read-only`, `plan` and `workspace`. `plan` is read-only, the writer is told to end with a plan, and a thread's writer gets `ask_user` to ask whether to go ahead; the go-ahead is a later run under another mode, so cedia still never waits mid-run. The mode is per run: each `run` thread event records it (`permission`), and a run that goes on in a session opened under another mode starts its message with a `<permission>` note, since the session's first message, which named the old one, never changes. `cedia permissions --json` lists the modes with the default for a client's picker (`PermissionList`); allow/deny rules (an `edit(…)` or `write(…)` deny rule covers both tools and also stops a command that may write and names a path it covers, as a word or a redirection target: `sed -i`, `cp`, `>`); built-in guards; then the sandbox (stage 2); then the classifier (stage 6, `core/trust/classifier.ts`): with `--classifier <ref>` (or `roles.classifier`), a model of the user's choosing reads each `exec` call that only the `workspace` mode let through (no allow rule named it, it is not read-only) before it runs, against the task, and answers ALLOW or BLOCK with a reason. It blocks what the task did not ask for and cannot be taken back or reaches past the project (pushing, publishing, deploying, deleting outside the working directory, changing the machine, sending data out, `curl | sh`); edits in the working directory never reach it, since snapshots can undo them, but a file a command names or implies (`sh run.sh`, `make` and its Makefile, `npm run` and package.json; at most 3, 4k characters each, inside the working directory, not named like a secret, redacted) is shown to it as it is now, so a script the writer wrote and then runs is read, not just its name. It reads the user's own words (the thread's first task, this run's prompt, the messages the user sent the thread, read again for each command; at most 6k characters, start and end), the command and those files, never the writer's reasoning, the plan or tool output. Each command is read in a session of its own, so one command cannot argue for the next; the system prompt stays cached across them. A command over 12k characters is blocked unread rather than read in part; an answer it cannot read, none, or a classifier that fails blocks, and the writer gets the reason like any denial. A stop while it reads leaves the call not started. Commands on the read-only list never reach it, so that list refuses every flag that runs another program (`awk` pipes and `getline`, `rg --pre`, `git grep -O`, …). Off unless named. Rules: flags > `CEDIA_PERMISSION` > `~/.cedia/settings.json`; a repo's `.cedia/settings.json` can only add deny rules |
| Guards | The deny list plus `secret-path` (credential stores, for every tool) and `secret-redaction`. A task that says to leave the existing tests alone ("do not change the existing tests", `leavesTestsAlone` in `core/trust/tests.ts`) protects the test files already in the working directory for that run: edit, write and any command that may write one are denied as `protected-test`, so new tests go in new files. A prompt rule alone left 1 protected test edited in 24 runs. Only the user lifts one, by name: `--unlock <guard>` or `permissions.unlock` in `~/.cedia/settings.json`. Never a repo, an allow rule or the model. cedia's prompt adds no content rules of its own. `context` in `~/.cedia/settings.json` (a string or lines) is the user's standing context, sent in the first user turn of every session as `<user_context>`; a repo cannot set it |
| Hooks | The user's own commands at three points, from `hooks` in `~/.cedia/settings.json` only (a repo must not run code outside the sandbox): `preToolUse` (after the policy allows a call: block it, or rewrite its input, which the policy then decides again), `postToolUse` (add a note to the result, or mark it failed, which a declared check it blocks counts as), `stop` (refuse a claim of done, which goes back to the model as a reminder; past 2 refusals the run ends `error_unverified_claim`). A hook is an argv run without a shell, outside the sandbox, with the scrubbed environment and a timeout (default 30 s, `timeoutMs`), in cedia's home rather than the workspace (an interpreter loads code from its working directory, which the repo or the model could plant), and its program is a name on PATH or an absolute path; the workspace is in its input. `match` takes an allow-rule pattern. Stop hooks judge the writer's claim only, not a plan, a review or a sub-thread's report. A stop of the run ends a hook at once. It reads one JSON object on stdin and answers by exit code: 0 goes on (stdout may hold `{decision, reason, updatedInput, note}`), 2 blocks with stderr as the reason; anything else (it cannot start, exits otherwise, times out) fails closed. What it says is made inert and capped before it reaches the model, and every run is a `hook` event |
| Privacy | No telemetry: cedia talks only to the model provider. Secrets in tool output (known token formats, private keys, dotenv/JSON/URL passwords) are replaced with `[cedia:redacted]` before the result is logged or sent, and a write carrying the placeholder is denied. `--privacy no-training` (default) refuses `dataPolicy: trains` models outside public repos; `zdr` allows only zero-data-retention models. flags > `CEDIA_PRIVACY` > user settings; a repo may set `zdr` but never loosen it |
| Edit tool | `edits[]` with tiered matching; `apply_patch` for GPT; edit mode chosen per model from eval results. An input in a shape models send by mistake (old_text and new_text at the top level, `edits` as a string) is put into the schema's shape before the policy sees it and logged as `input_repaired`; the assistant event keeps what was sent. Results count repairs by tool and kind (`inputRepairs`), and eval summaries per model, which is the number that picks the edit mode |
| Diagnostics (LSP) | After a successful `edit` or `write`, the result adds the file's errors as a language server reports them (`core/lsp/`): at most 10, by line, warnings left out, nothing when there are none, so a type error is seen at the edit that made it. Known servers are used when installed (on PATH or in the project's `node_modules/.bin`): `typescript-language-server`, `pyright-langserver`, `gopls`; `lsp` in user settings adds others or turns them off (`false`), and `--lsp off` turns them off for a run. A server starts at the first edit it covers and stops with the run, with everything it started; it runs as bash does, in the OS sandbox with the scrubbed environment, and only when the permission policy would let bash run its command line, since some run the project's own code (tsconfig plugins, build scripts, a server in `node_modules/.bin`). The file is opened for each edit and closed after, so the server reads every other file from disk and never holds a copy that bash or a formatter changed since; publications for an older version are dropped, and an empty one is waited on a little longer (600 ms) in case a later step finds errors. A clean edit costs about 1 s with typescript-language-server or pyright. One that does not start, or stops, is reported once on stderr and not tried again; one that publishes nothing in time (15s for the first file, 5s after) adds nothing, and an abort stops the wait. A work sub-thread in a worktree gets none, since the servers read the parent's directory |
| Search | `grep` (`core/tools/grep.ts`, effect read) searches file contents with ripgrep, which skips what `.gitignore` and `.ignore` exclude, so a question on a large repository does not read build output: on a 2.8 GB tree the writer's `grep -r` in bash took 22 s and rg 0.16 s. It takes `pattern`, `path`, `glob`, `ignore_case` and `files_only`, returns `path:line:text` (lines cut at 300 columns) and at most 200 lines with a count of the rest. Files named like credentials are never searched, as `read` never opens them. Without rg it runs `git grep` in a repository, and elsewhere says to use bash. Plan and review get it with the other read tools |
| Tool output | A result holds at most 30k characters. Longer bash output goes whole to a file, redacted like a result, readable only by the user, in the temp dir (`cedia-output-<uid>/<session>/<call>.txt`, used only when each directory is a real one the user owns and others cannot open; a week after its session it is removed; outside cedia's home so `read` and a sandboxed `grep` reach it); the result shows its start and end and the path, and the log records it as `spillPath`. Other tools cut in the middle (`read` pages with `offset`) |
| Images | `-p --image <file>` (repeatable) shows the writer the image with the prompt, before its text, and the task names the file so plan and review (text only) can open it; `read` on a PNG, JPEG, GIF or WebP returns the image (`core/images.ts`). The format and size come from the file's header, never its name. An image the Claude API would refuse (over 8000 px a side or 10 MB of base64) is refused before it is stored; cedia does not resize. The bytes go once into `~/.cedia/blobs/<sha256>` (0600 in a 0700 directory) and the log holds `ImageRef{sha256, mime, width, height, bytes, name}`, so a request rebuilt from the log sends the same bytes and the cache holds; a blob that no longer matches its hash stops the request. A session shows at most 20 images (past 20 the API wants every image at most 2000 px); later ones are dropped with a note in the result. Anthropic Messages sends image blocks (in a tool_result's content for a tool's); Chat Completions and Responses, whose models here read text only, get a note in each image's place. MCP images are still left out |
| Projects and threads | A project is a working directory, and every git worktree of a repository is the main worktree's project (`projectRoot` via `git rev-parse --git-common-dir`), so threads in different worktrees list, message and recall one another; the session event's `cwd` names the worktree, and snapshots stay per worktree. Every headless run is a thread of it (`~/.cedia/projects/<slug>/threads/<id>.jsonl`, append-only, so two cedia processes can write one without locks). `--thread <id>` goes on with a thread: in its last session when the model is the same, otherwise in a new session that starts from its latest handoff note or result. `cedia threads [list|show|send|archive|rename|delete]`. Append-only stops at delete: `threads delete` removes the thread's file, its sub-threads' and the session logs they name (one another thread names too stays), refuses a thread whose run is going on unless `--force`, and keeps blobs and worktrees (`core/project/delete.ts`). Modeled on Claude Projects' threads (each starts from the project's files, instructions and memory; threads run in parallel and can be resolved), built from the public docs and from using it, nothing reverse-engineered. **Multi-repo workspaces (decided 2026-10-25):** a project may be a *workspace* of several repository roots, so one coordinator can open a thread per repository, each in its own worktree with its own PR, as Claude Code Projects does ("one goal across many repositories"). The project key becomes a workspace key; a thread carries the root it runs in; memory, schedules and thread files are workspace-keyed, instructions are per-root (each root's AGENTS.md/CLAUDE.md). A single-root workspace keeps the current behaviour. The client names the workspace in `CEDIA_ROOTS` (repository roots separated by colons, the primary root first; `core/session/log.ts` `workspaceRoots`). `open_thread{task, title?, root?}` records the root on the new thread's `open` event and refuses one that is not a root of the workspace; a `--thread` run whose recorded root is another repository than `--cwd` runs in that root; `cedia threads list` shows the root; threads, sessions, `cedia memory` and `schedules` of every root are keyed by the primary root's slug. The writer's environment names the workspace's other roots as read-only: reads reach them as they reach any path, and a change there is a thread of its own in that root (done 2026-10-28). Local roots only — no cloud clone or GitHub App. The workspace key is the primary root's slug (the first root, the repository the project started from), so a single-root project keeps its files where they are; the other roots are extra, and the primary root is never removed from a workspace (decided 2026-10-28). |
| Project instructions | The repository's AGENTS.md (or CLAUDE.md where a directory has none) in each directory from the repository's root down to the working directory, root first, with `@path` lines brought in (`core/project/instructions.ts`). They go in the first user turn after the environment, never the system prompt, framed as `<project_instructions path>` and made inert, 40k characters at most. They are the repository's words: an import may only name a file inside the repository (a symlink out counts as outside), and the permission mode, sandbox and deny list decide whatever they say |
| Memory | Project memory: short facts that outlive a thread, in `~/.cedia/projects/<slug>/memory.jsonl` (append-only; forgetting is an event). The user keeps them with `cedia memory add|forget`, the writer with the `remember` tool (at most 500 characters a note; denied in read-only sessions, absent in plan, review and sub-thread sessions). Every new session gets them in its first turn after the project instructions, newest first past 8k characters, made inert, with a line saying a note may be out of date. A run reads them once at its start, so a note written mid-run reaches the next run, never a cached prefix; notes are labeled by who kept them and redacted like tool output |
| Skills | A folder with a `SKILL.md` (Agent Skills format: front matter `name` and `description`, then instructions) and the files it uses (`core/skills/skills.ts`). Found in `~/.cedia/skills` (the user's, which win a name) and in `.agents/skills`, `.claude/skills` and `.cursor/skills` from the working directory up to the repository root, nearest first; at most 50. Only names and descriptions go in the first turn, in a `<skills>` frame capped at 8k, so the system prompt and the tool list stay the same across repositories; the `skill` tool (read effect; writer, reviewer and sub-threads, present only when there are skills) loads a skill's text and lists its files, or reads one of them with `file`. A repository's skill is the repository's words, like its AGENTS.md: a folder that resolves outside the repository is left out, files are read only inside the skill's folder, never when named like a secret, at most 256 KB, and everything is redacted and inert. `cedia skills` lists them. Each skill is also a `/` command: `cedia commands --json` (`CommandList`: name, description, `argument-hint` from the front matter, source) is what a client offers when the person types `/`, and a prompt that starts with `/<skill>` goes to the writer as typed with a line asking it to load that skill first (the skill still comes through the tool, framed as ever). A prompt that starts with `/` and names no skill is left alone. Skills say how to do a kind of task; they cannot widen the permission mode or the sandbox |
| MCP | The user's MCP servers (`mcpServers` in `~/.cedia/settings.json`: a `command` with `args`, `env` and `cwd`, or a `url` with `headers`; `${VAR}` in env values and headers comes from the environment). A repository cannot add one, since a server is a program cedia would start. cedia's own client (`core/mcp/`): the handshake, `tools/list` and `tools/call` over stdio or streamable HTTP, nothing else; a server's requests get "method not found" except ping. Servers start once per run, before the first request, in name order, and their tools are `mcp__<server>__<tool>` in name order, so the tool list stays cacheable; one that fails to start is left out with a note. A local server gets only PATH, HOME, the locale and the like from cedia's environment, never its API keys. Each tool counts as `exec` (workspace mode, or an allow rule naming it in read-only), unless the server is marked `readOnly: true`; reviewers and sub-threads get only read ones. A call times out after 120s (`timeoutSec`) and stops with the run; results are tool output like any other, images and audio left out with a note. A resumed session whose server is gone keeps the tool, and a call says the server is not there. `cedia mcp list|check|add|remove` (`core/mcp/manage.ts`, capability `mcp.manage`) is how a client's settings page manages them, so cedia stays the one writer of `mcpServers`: a listing names env variables and headers but never their values, a check starts the server as a run would and lists its tools, and an add that a run would refuse is refused. The file is written whole through a temporary file |
| Plugins | Plugins in the Claude Code layout (`.claude-plugin/plugin.json` or `plugin.json`, `skills/<name>/SKILL.md`, `commands/<name>.md`, `.mcp.json`, `hooks/`, `agents/`), so published ones work unchanged (`core/plugins/plugins.ts`). `cedia plugin install` takes a folder, a git URL or `github:<owner>/<repo>` (a shallow clone), or `<plugin>@<marketplace>` from a marketplace added with `cedia marketplace add` (its `.claude-plugin/marketplace.json`; a plugin's folder must be inside it, or a GitHub or git source); the plugin is copied to `~/.cedia/plugins/<name>`, its name one path segment, and `update` installs from the same source again. A repository never adds one. An enabled plugin's skills and commands join the skill list as `<plugin>:<name>`, after the repository's, read only inside its folder, redacted and made inert like a repository's; a command (a Claude Code slash command) is loaded like a skill, with a line saying where `$ARGUMENTS` and `` !`cmd` `` come from, and `/<plugin>:<name>` asks for it. Nothing a plugin ships runs on its own: its MCP servers go into `mcpServers` as `<plugin>-<server>` only when the user runs `cedia plugin mcp <name>` (`${CLAUDE_PLUGIN_ROOT}` is the installed folder; checked as `cedia mcp add` checks; removed with the plugin), and its hooks and agents are listed by `cedia plugin show` and never run: a Claude Code hook is a shell line run outside any sandbox and written for Claude Code's tools |
| Web | `web_fetch{url, offset}` (`core/tools/web.ts`) on every session: one page by GET, HTML turned into readable text in one pass (title, headings, lists, links, code), long pages in 29k-character parts, at most 5 MB read, 30s. It reaches what the session's shell may reach, so it is no way around the sandbox or a read-only session: the domains the user named (`--allow-domain`, `sandbox.allowedDomains`, matched as the sandbox matches them), plus any public host when the sandbox is off and the session may run commands; an allow rule widens it (`web_fetch`, `web_fetch(<domain>)`). Never a private, loopback, link-local or other special address, in any of the forms an IPv6 address can carry an IPv4 one, unless the user names that host; never a URL with credentials; every redirect hop is checked like the first URL. The name is resolved once and the request goes to the address checked, so a short-lived DNS answer cannot turn it elsewhere (through an HTTP proxy the proxy resolves it). Pages are tool output: data, made inert and redacted like any result. Search is not built in: an MCP server for a search engine adds it |
| Browser | `browser{action, url, control, text, submit, key, direction, offset, full}` (`core/tools/browser.ts`) on writer sessions of a run given `--browser <endpoint>`: a page of a Chromium the client started (the desktop's daemon runs one per workspace, shown in its Browser pane, so the person and the model see the same page), driven over the DevTools protocol with no library. cedia starts no browser. The endpoint is `http://host:port` (its first page, else a new one) or one page's `ws://…/devtools/page/<id>`. Actions: open, read (the page as text, each visible control numbered `[3 button "Sign in"]`, long pages in parts), click and type by number (real input events; type replaces a field's text, picks a select's option, submit presses Enter), key, scroll, back, console (the page's console messages and exceptions), screenshot (the visible page, or all of it with `full`, as a PNG the model sees, stored like `read`'s images and counted in a session's 20). Each step answers with the page after it. It opens what web_fetch reaches plus loopback (the preview), widened by `browser` and `browser(<domain>)` allow rules; every document the page loads is checked through Fetch interception (links and redirects too) and a refused one is aborted and the page taken back; never file:, data: or another non-http URL, credentials in a URL, or an unnamed private address. The page's own subresources are not checked. open, read, scroll, back, console and screenshot count as network; click, type and key as commands (a read-only session needs an allow rule). A resumed session that had the tool keeps it on a run with no browser, and a call says none is connected. |
| Handoff | Instead of compacting, a writer session whose context passes `handoffAt` (flag `--handoff-at`, `handoffAt` in user settings; default half the window, at most 150k (115k where a cache read costs a twentieth of input, Opus 5.5 and Sonnet 5.5: a replay of the 65 sessions on file past 60k put the cheapest point at 80k to 90k there, 115k 0.8% above it and 150k 2.1%), and below any long-context price) has doubled since its first reply, and, if it picked up from another session, has changed a file itself (a note cannot carry what was read, so a chain of sessions that only read would each read it all again; a first session may hand off before its first change, since on Haiku it otherwise read on past the 100k price line and handed off after its first edit anyway) is asked for a handoff note at the next turn boundary, while its prefix is still cached. The note carries the plan for what is left, concrete enough to follow, and the new session is told to carry it out rather than plan again: in the repo evals each successor re-read the code and spent 30k to 40k thinking tokens (about 2.5 minutes on Haiku) re-planning, which filled its context again after one file. A new session of the thread starts from the task and that note; it has `parentSession`, inherits the changed files for the done gate, and gets a `recall` tool that searches the earlier sessions' full logs. Nothing is edited, so thinking signatures and caches stay valid, and nothing is lost. At most 8 per run. On the Claude API models the default (`--handoff compact|note`, `handoff` in user settings) is Anthropic's on-demand compaction instead of the note: on the long three-changes runs it cost 31% less and took 14% less time, 3 of 3 passing either way. It runs on the Claude API models (OpenCode Go drops its beta header): past 85% of the handoff point the provider summarizes the session up to an earlier request in the background, keeping at least the newest quarter of the context, while the session goes on; at the next turn boundary after the summary arrives (waiting for it at the handoff point) the session ends, and the next one starts from the signed summary block followed by copies of every event after the summarized request, thinking included (`core/project/compact.ts`). The kept turns' thinking stays valid because the provider wrote the summary on the same model, system prompt and tools, and they directly follow the messages it summarized. Such a session starts large by design (the kept turns and those that ran while the summary was written), so it hands off once it has grown by the kept share rather than doubled. A compaction that brings no summary hands back to the note |
| Sub-threads | The writer's `spawn{task, kind}` tool hands self-contained work to a child session with a fresh context; only its report (at most 4k characters) comes back. The model names the kind and cedia decides how it runs: `explore` is read-only on the `swarm` model (the code model under `zdr`) and runs in parallel, at most 4 at a time; `work` may write, on the writer's model under the run's policy, sandbox and checks, alone and between two snapshots, so the parent's ledger records its changes. A run starts at most 16 sub-threads. A child is its own thread with a `parent`, archives itself when it succeeds, stays listed when it fails, and cannot spawn. A `work` child hands off at the run's handoff point like the writer, to a new session of its own thread that gets `recall` over the child's earlier sessions (on Haiku a child past 100k would pay the long-context price every turn); `explore` never hands off, since a session that only read has nothing a note could carry. A writer that has not spawned is reminded of the tool once, when its context passes a third of its handoff point (in the repo evals Haiku never spawned unprompted, even at 170k). A sub-thread's spend counts against the run's `--max-budget-usd` as it happens, and the run's result counts sub-threads by kind, the handoffs their sessions made and the largest context one saw (`spawned`; `peakContext` is the run's own sessions'). With `--spawn worktree` (or `spawn: "worktree"` in user settings) each `work` child runs in a git worktree of its own, at most 4 at a time beside the writer's other calls of the turn (`core/project/worktree.ts`): detached at HEAD in a private directory of the temp dir, filled with the parent's working tree as it is (uncommitted changes under the parent's working directory included; elsewhere in the repo it is HEAD, and only changes under that directory come back), with what git ignores there brought in so the checks run (directories such as node_modules as links, small files such as .env as copies), never recorded or applied. In the sandbox its bash writes only inside its own worktree (and the sandbox's `$TMPDIR`), so it can reach neither the parent's files, nor the other worktrees, nor what the links point to; with the sandbox off nothing stops it, as nothing stops the writer. Its changes come back when it ends, however it ended (a child whose check cannot pass until another's part lands is common, and the parent must check after it anyway; only a stop leaves them out), as a three-way merge in the snapshot store (base: the tree it started from; ours: the parent's tree now; theirs: its tree), written between two snapshots of the parent one child at a time (the `isolated` call class: it runs beside other calls and writes only through `ctx.write`). A lockfile (`bun.lock`, `package-lock.json`, `Cargo.lock`, `go.sum` and the other common ones, by name) or a file `.gitattributes` marks `linguist-generated` or `lww` that both sides changed is not merged by lines: the side that wrote it last (its mtime) wins it whole, and the report names it and whose was kept, so the parent can regenerate it (LayerFS's `.lww`; `core/project/newest.ts`). A merge with any other conflict writes nothing; a file the parent's own edit could not write (its deny rules, secret stores, `.git`, `.cedia`, hooks) or the sandbox keeps from bash (its protected dotfiles), and a nested repository, are left out; either way the report says so and the worktree stays for the parent to read, and a week later it is removed. Its snapshots use cedia's own git dir, never the worktree's `.git` file, and run only once its directory is checked to be the one made (the same inode, no link on the way), since the child could have changed both. Outside git, or before the first commit, a work child runs in place and alone as without worktrees. Best of N (`core/project/bestof.ts`): with worktrees on, `spawn` takes `approaches` (2 to 4, kind `work` only), and one work child tries each at once, in a worktree of its own, with the task and its approach; when all have ended cedia runs the run's checks (declared, else detected) itself in each worktree, in that child's sandbox, and keeps the one that passes most (then one that ended in success, then the fewest unverified files, then the cheapest). Only the kept one is merged back; the others' worktrees are removed. The report lists every try with its checks and thread. Checks cedia ran decide, not the children's claims, so the tries are judged by the same commands. Each try counts as a sub-thread against the run's 16; the call takes one work slot. A resumed session keeps the spawn tool it was opened with. `--spawn on|off|worktree`, `--swarm <ref>` |
| Thread messages | `threads`, `read_thread` and `message_thread` tools (present when the project has another thread): a message is appended to the other thread's file and shown to it as a logged reminder at its next turn boundary, or when it is resumed. `message_thread` is `write_workspace`, so read-only sessions cannot send. The user sends with `cedia threads send`, which prints the message id, and takes back one no session has seen yet with `cedia threads unsend`. A message that was delivered stays delivered whatever the order of the two lines, and an unsent one never reaches a model, `read_thread` included |
| Questions | With `--ask on` (or `ask: true` in user settings; default off, since a headless run has nobody to answer, and the desktop turns it on), a writer session of a thread gets `ask_user{question, options?}`. It ends the run once the turn's other calls are done: the result is `asked` (exit code 0) with `question`, the session's last `turn_end` has reason `asked`, the thread gets a `question` event and the state `asking`. The answer is the thread's next prompt (`cedia -p <answer> --thread <id>`), sent framed with the question. The tool's description keeps the bar high, as the owner asked (2026-10-22): threads keep working and check their own work, and ask only for a decision that changes the goal, a step that cannot be undone or costs money beyond the task, or something only the owner has. Sub-threads, plan and review never get it. A question is not a permission prompt: the policy still decides every call |
| Todo list | With `--todo on` (or `todo: true` in user settings; default off, and the desktop turns it on), a writer session of a thread gets `todo{items: [{text, state: pending|doing|done}]}` (at most 20). | Profiles and open_thread | `--profile <name>` picks a named set of defaults that sit under the flags (a flag still wins): `model`, `permission`, `spawn`, `ask`, `todo`, `openThread`, and `instructions`, which go in the writer's first message as `<profile name="…">` (`core/profiles.ts`). At most 8 per run. `cedia threads list` shows `(opened by <id>)` |
| Schedules | A prompt for a thread at a time, once or every so often (`every` at least 5 minutes), kept in `~/.cedia/projects/<slug>/schedules.jsonl` (append-only: `add`, `enabled`, `cancel`, `fired`; `core/project/schedules.ts`). cedia never runs anything at a time itself, since nothing of it lives between runs: whoever runs the project's threads (the desktop's daemon, or cron) asks `cedia schedules due --json`, records each run it starts with `cedia schedules fire <id>`, and runs `cedia -p <prompt> --thread <thread>`. A profile with `schedule` (the coordinator) gets `schedule{prompt, at, every?}` or `{cancel}` for its own thread, answered with that thread's schedules; `at` is an ISO time or a delay (`30m`, `2h`). ## Architecture

Clients (TUI, headless `-p`, eval runner) talk to the core over one protocol. Inside the core every event is written to the session log first, and the context builder builds the next request from that log, so resume, fork, compaction and evals take the same path.

```
src/
  cli.ts
  core/        no UI; tested with a faux provider
    loop/ session/ context/ providers/ tools/ safety/ trust/ project/ skills/ hooks.ts roles.ts
  protocol/    command and event types + JSONL codec
  clients/     tui/ headless/
evals/         tasks/, run.ts, baseline/
```

Rule enforced by a test: `src/core` and `src/protocol` never import from `src/clients`.

Session files live at `~/.cedia/sessions/<project-slug>/<id>.jsonl`. The first line is a `session` event `{cwd, parentSession?, thread?, role, createdAt}`. The leaf is the last event; a fork is a new file whose first event's `parentId` points into the source.

## Core shapes

These are fixed before stage 1 code is written. Names may change; the information each one carries may not shrink.

```ts
// Assistant content keeps each wire's opaque reasoning payload so it can be replayed byte for byte.
type AssistantBlock =
  | { type: 'text'; text: string; sig?: string }
  | { type: 'thinking'; text: string; opaque?: string; redacted?: boolean; ms?: number } // ms: from its first delta to its end
  | { type: 'tool_use'; id: string; callId?: string; name: string; input: JsonObject; inputError?: string }
  | { type: 'compaction'; text: string; opaque: string }; // a provider-written summary and its signature
// The assistant event records which wire produced it; blocks are only replayed to the same wire. costUsd is the
// reply's cost at the model's price when it ran, so a client shows a run's spend as it grows; a block's ms and the
// event's costUsd never reach a provider.
type AssistantEvent = { kind: 'assistant'; wire: Wire; model: string; blocks: AssistantBlock[]; stop: StopReason; usage: Usage; costUsd?: number };
type StopReason = 'end_turn' | 'tool_use' | 'max_tokens' | 'refusal' | 'aborted' | 'error' | 'compaction';
// Handoff by compaction: the request (`of`: the request whose messages it summarizes) and its outcome in the old
// session; first in the new one, the summary, followed by `kept` copies of the old session's events.
type CompactRequest = { kind: 'compact_request'; of: EventId; bodyHash: string; headers: Record<string, string> };
type Compaction = { kind: 'compaction'; requestId: EventId; stop: StopReason; usage: Usage; block?: CompactionBlock; error?: AttemptError; ms?: number };
type Summary = { kind: 'summary'; session: string; block: CompactionBlock; kept: number };

// Provider boundary. One adapter per wire; the loop never sees wire JSON.
type Provider = { wire: Wire; stream(req: WireRequest, signal: AbortSignal): AsyncIterable<StreamEvent> };
type StreamEvent =
  | { type: 'start' }
  | { type: 'text_start' | 'text_end'; index: number } | { type: 'text_delta'; index: number; delta: string }
  | { type: 'thinking_start' | 'thinking_end'; index: number } | { type: 'thinking_delta'; index: number; delta: string }
  | { type: 'toolcall_start'; index: number; id: string; name: string } | { type: 'toolcall_delta'; index: number; delta: string } | { type: 'toolcall_end'; index: number }
  | { type: 'done'; message: AssistantEvent }
  | { type: 'error'; error: AttemptError };

// Every turn ends with one turn_end event, including aborts.
type TurnEnd = { kind: 'turn_end'; reason: 'completed' | 'aborted' | 'error' | 'max_tokens' | 'budget' | 'max_turns'; cause?: 'user' | 'parent' | 'hook' };

type AttemptError = {
  code: 'rate_limit' | 'overloaded' | 'auth' | 'bad_request' | 'network' | 'timeout' | 'server' | 'context_length' | 'quota';
  status?: number; retryAfterMs?: number; message: string;
};

// Headless result. Exit code 0 only on 'success'.
type HeadlessResult = {
  type: 'result';
  // 'handoff' ends a session, never a run: the client goes on in a new session of the thread.
  subtype: 'success' | 'error_max_turns' | 'error_max_budget_usd' | 'error_during_execution' | 'interrupted' | 'error_unverified_claim' | 'error_stuck' | 'handoff' | 'asked';
  sessionId: string; numTurns: number; usage: Usage; costUsd: number; cacheHitRatio: number; result: string; evidence?: Evidence;
  timing?: Timing; plan?: Step; review?: Step & { verdict: 'approve' | 'changes' | 'unclear'; fixed: boolean };
  thread?: string; sessions?: string[]; subthreads?: number;
  compaction?: { block: CompactionBlock; of: EventId }; // a 'handoff' by compaction
};
type Step = { model: string; via: 'cedia' | 'claude-code'; sessionId: string; costUsd?: number };

// A thread file is append-only JSONL; the thread is the fold of its events (core/project/threads.ts).
type ThreadEvent = { at: string } & (
  | { kind: 'open'; title: string; task: string; parent?: string }
  | { kind: 'session'; sessionId: string; model: string; role: string; why: 'start' | 'resume' | 'handoff' | 'quota' | 'rejected'; path?: string }
  | { kind: 'handoff'; sessionId: string; note: string }
  | { kind: 'message'; id: string; from: string; text: string } // from: a thread id or 'user'
  | { kind: 'delivered'; ids: string[]; sessionId: string }
  | { kind: 'unsend'; ids: string[] } // the user took back messages; a delivered one stays delivered
  | { kind: 'rate'; rating: 'up' | 'down'; sessionId?: string; note?: string } // never reaches a model
  | { kind: 'question'; sessionId: string; question: string; options?: string[] } // ask_user; the state becomes 'asking'
  | { kind: 'state'; state: 'working' | 'done' | 'failed' | 'stopped' | 'asking'; result?: string }
  | { kind: 'archived'; archived: boolean }
  | { kind: 'title'; title: string }); // threads rename; the latest is the title, and a rewind keeps it

// Per-model facts the adapters and the loop branch on.
type ModelCapabilities = {
  reasoning: 'anthropic-thinking' | 'reasoning_content' | 'responses-item' | 'none';
  replayReasoning: 'required' | 'forbidden' | 'same-turn';
  parallelToolCalls: boolean; input: ('text' | 'image')[]; effortLevels: string[];
  cacheMinTokens: number; midConversationSystem: boolean; midConversationEffort: boolean; contextWindow: number;
};

type ToolOutput = { text: string; isError: boolean; images?: ImageRef[]; … }; // ImageRef: core/images.ts
```

Rules that go with the shapes:

- **Abort.** `signal` aborts the stream; the adapter emits `done` with `stop: 'aborted'` and whatever blocks were complete. Unfinished tool calls get synthetic `tool_result`s. The turn ends with `turn_end{reason:'aborted'}`.
- **Retry.** `rate_limit`, `overloaded`, `network`, `timeout` and `server` retry with exponential backoff, at most 5 attempts, honouring `retryAfterMs`. `auth`, `bad_request`, `context_length` and `quota` (HTTP 402, or a 429 whose message says the plan or balance is spent) never retry. Each try is its own `attempt` event.
- **Request event.** Carries model, effort, `toolsHash`, `systemHash`, `bodyHash`, TTL and header names with value hashes. Never header values.
- **Role fallback** starts a new session on the fallback model; it never swaps the model inside a session (cache rule 5).
- **Quota fallback.** A run that ends on a `quota` error continues on its fallback model (`--fallback`, then `fallback` in `~/.cedia/settings.json`, then the built-in `deepseek` → `anthropic/claude-haiku-5-5`; `none` turns it off; a repo cannot set it). The new session has `parentSession`, a logged reminder that the tree may hold part of the work, what is left of the turn and budget limits, and the first session's changed files as writes the done gate must still see verified. The result adds up both sessions' spend and turns. `--on-quota wait:<minutes>` (or `onQuota` in `~/.cedia/settings.json`; a repo cannot set it) first waits in the same session for a spent quota that says when it comes back (a 429 with `retry-after`), up to that many minutes across the run, and falls back only past it; a spent balance (402) says no time and falls back at once. Each wait is an `attempt` and goes on stderr; SIGTERM ends it.
- **Refused history.** A `bad_request` or `context_length` error on a request after the session's first accepted one means the provider no longer takes the session's history (a thinking signature it rejects, a tool call it cannot read back, a context past the window), and resending it fails the same way. cedia never edits history (Claude Code drops all thinking and retries), so the run goes on in a new session on the same model, once per run, the way quota fallback does: `parentSession`, the first session's changed files for the done gate, `recall`, and a logged note that the tree may hold part of the work. A resumed thread whose last session was refused starts a new session instead of resuming it.
- **Cold resume.** `--thread` goes on in the thread's last session when the model is the same, unless that session's cache has expired (its last reply is older than its TTL), its context is past 30k tokens, and re-reading it uncached would cost more than twice what a new session's start does (system prompt, tools, preamble, the thread's note or result, the task). Then it goes on in a new session from where the thread stopped, with `recall`, and stderr names both prices. On Opus 5.5 a cold 150k session costs about $0.75 to resume against about $0.06 for a 12k start.
- **Malformed turns.** A reply with no text and no tool call (thinking only, or nothing) gets one reminder; a second in a row ends the run with `error_during_execution`, so an earlier turn's text never stands as the result. A `refusal` ends the run with `error_during_execution`. A tool's output is always a string by the time it is logged (an object is JSON, nothing is an error result). Calls in one reply that share an id run once and get one result, since the wire pairs results by id.
- **Mid-conversation system prompt.** Appended as a system message when `midConversationSystem` is true, otherwise as a user text block.
- **Effort escalation.** A session starts at `--effort` (else the model's default) and moves to `--escalate` (default `high`, `off` turns it off) once, the first time the done gate refuses a claim. Only on models with `midConversationEffort` (Anthropic's per-message effort, beta `mid-conversation-output-config-2026-07-01`) and only upward. The change is an `effort` event logged right after the gate's reminder, the user text that carries it (a change waits for a user turn with new input, and a turn of tool results alone is not one); the adapter sends it as a `role: "system"` message with empty content and `output_config.effort`, so the top-level effort and every earlier message stay as sent and the cache holds. Soft checks never escalate. A failed check does not escalate either: the note it needs to carry the change made Haiku 5.5 at `low` give up sooner on `hard-redact-bugs` (refused both gate runs, which pass at `low` without it). Anthropic measured the policy as a re-run: Opus 5.5 at `low` with failures re-run at `high` solved about 97% of SWE-bench Pro for $0.17 a task, against 95% for $0.29 at `high` throughout (`about-claude/models/optimizing-for-cost-and-intelligence.md`).
- **Parallel tools.** Calls whose `ToolSpec.effect` is `read` or `network` run in a bounded pool (8 at a time); `write_workspace` and `exec` run alone, as ordering barriers. `tool_intent` events are written in assistant block order; results go back as one batch (Anthropic requires all results of a turn in one user message).
- **Permission order in the log.** `assistant → permission → tool_intent (only if allowed) → tool_result`. A denied call gets `tool_result{status:'denied'}` and no `tool_intent`.
- **Result in the log.** A run that ends with a result writes it, receipt and evidence included, as `result{result: HeadlessResult}` right after the last `turn_end` of its last writer session, so a client that rebuilds a thread from the files shows its last receipt. It is not streamed as an event (the stream already ends with the result line), and the context builder skips it, so no model sees it. A resumed session goes on after it.
- **Token estimate.** The last response's `usage` plus `chars/4` for the delta; Anthropic `count_tokens` on demand.
- **Faux provider.** A script is an array of assistant messages or factories `(context, state) => AssistantEvent`, emitted as delta-level `StreamEvent`s. It computes `usage` by hashing the prefix it was sent, so `cacheRead` is nonzero exactly when the prefix repeats. Shape modeled on pi's faux provider (MIT); add a NOTICE entry if code is adapted.

Protocol events (core → client): every session event, plus `stream` (the `StreamEvent`s of the current attempt), `turn_end` and `result`. Commands (client → core): `prompt`, `abort`, `resume`, `fork`. There is no permission reply: cedia never stops to ask for permission. A question for the owner ends the run instead (Questions, above).

## Cache rules

Taken from the DeepSeek harness (`packages/core/agent-loop/README.md`, "KV Cache effect") and Claude Code's prompt caching docs.

1. The prefix stays byte-identical: tools in a fixed order, system prompt sections in a fixed order, no paths or per-process values in the cached part.
2. A system prompt change mid-session is appended as a system message, never written into message 0.
3. The tool list is frozen at the first request; later tools come through tool search or an appended announcement.
4. Cancelled tool calls get synthetic results appended; history is never cut.
5. Roles change only when a subagent starts. The main session never switches model; each subagent owns its cache.
6. A session waiting on a long tool (a work sub-thread, a slow check) keeps its prefix cached: on Anthropic, while tools run past 4 minutes after a request was sent, the same body goes again with `max_tokens: 0` and no stream every 4 minutes, which refreshes the 5-minute cache at the cache-read price instead of writing the whole context again on the next request. Each refresh is a `keepalive` event with its usage, counted in the session's cost.
7. Between prompts the owner may think for longer than 5 minutes, so in the TUI the writer's breakpoints carry `ttl: "1h"` on the Anthropic wire (`--cache-ttl 5m|1h`; `-p` defaults to 5m, plan, review and sub-threads always do). An hour's write costs 2× input against 1.25×, so it pays once one pause in about eight prompts runs past 5 minutes, at Opus 5.5's prices a whole rewrite of a 40k context ($0.20) against about $0.02 a prompt. With 1h the refresh while tools run comes every 55 minutes. `Usage.cacheWrite1h` is the part of `cacheWrite` written for an hour, billed at 2× input.

Per provider: Anthropic uses automatic `cache_control` plus a breakpoint at the end of tools and system; OpenCode Go requests carry a stable `x-opencode-session` and cedia's own User-Agent; Responses requests carry `prompt_cache_key`. Each `request` event records model, effort, tools hash, system hash, body hash, TTL and header names, so a miss can be traced to what changed.

`Usage` keeps disjoint `uncached / cacheRead / cacheWrite / output` fields (`cacheWrite1h` is part of `cacheWrite`). Mapping per wire:

| Wire | cacheRead | cacheWrite | uncached |
|---|---|---|---|
| Anthropic Messages | `cache_read_input_tokens` | `cache_creation_input_tokens` | `input_tokens` |
| Chat Completions | `prompt_tokens_details.cached_tokens`, or DeepSeek `prompt_cache_hit_tokens` | 0 | `prompt_tokens` minus cacheRead |
| Responses | `input_tokens_details.cached_tokens` | 0 | `input_tokens` minus cacheRead |

Reasoning tokens are a subset of `output`. Hit ratio = cacheRead / (uncached + cacheRead + cacheWrite).

Providers cache in blocks (`cacheBlockTokens`): DeepSeek in 128-token blocks, and Anthropic reads stop a few tokens short at the turn boundary. A read is a miss only when it falls more than one block short of the previous input. Measured numbers live in `evals/cache/`.

Claude 5.5-family models also bind thinking signatures to the prefix, so any history edit is a correctness bug, not just a cache miss. Stage 4 checks this three ways: diff captured requests turn to turn; run with `prefix_mismatch_behavior: "drop_block"` (beta `thinking-binding-controls-2026-08-01`) and log any `input_transformations`; then set the field explicitly.

## Desktop client

cedian (`pondtakesqueen/cedian`) is the native macOS desktop for cedia: it runs cedia, draws its threads as panes and never runs an agent loop of its own. What it builds on, and what it may not do:

- Shapes come from `src/protocol/protocol.schema.json`; replays come from `test/fixtures/sessions/`. A change to either is a deliberate regeneration in the same PR as the type change.
- `cedia --version --json` prints `VersionInfo`: the version, `protocol` (the first 16 hex digits of the sha256 of the `protocol.schema.json` the build carries, so the desktop can tell whether its pinned schema matches) and `capabilities`, the features a client may branch on. A capability is added when its feature lands and never renamed.
- A prompt is one run: `cedia -p <text> --thread <id> --output-format stream-json`, in the thread's worktree. Text sent while it works goes in with `cedia threads send`, delivered at the next turn boundary, and `cedia threads unsend` takes it back until then; SIGTERM aborts. The user's 👍/👎 goes in with `cedia threads rate`.
- The receipt of a thread's last run is the last `result` event in its sessions' logs; the live stream's final line is the same object.
- Thread and session files are cedia's to write. The desktop reads and indexes them and changes them only through cedia commands.
- Who runs a project's queued threads and due schedules (decided 2026-10-28): the desktop's daemon on a Mac where it runs. It holds a lock that `cedia daemon` checks before each pass and yields to, so no thread starts twice; `cedia daemon` (or cron) runs them only where the desktop does not. The lock is `~/.cedia/desktop.lock`, `DesktopLock{pid, at}`, which the desktop writes while it serves and removes when it stops; a pass that finds a live holder starts, fires and reaps nothing (`yielded` in its tick), and a lock whose process is gone or that does not parse holds nothing (`core/project/desktop-lock.ts`, capability `daemon.desktop-lock`).
- Inline edit and tab completion are cedia commands for the desktop's v1 (owner, 2026-10-28), since cedia is the only agent. Inline edit is built: `cedia inline-edit --file <path> --range <line:col-line:col> --instruction <text> [--stdin] [--model <ref>] --json` prints `InlineEdit{file, range, replacement, patch, model, costUsd}` (`core/project/inline-edit.ts`, capability `inline-edit`). Lines and columns count from 1, columns in UTF-16 units as an editor counts them, and an empty range asks for text inserted there; `--stdin` takes the file as the editor has it, unsaved changes included. One reply on the code model (or `--model`) in a session of its own with no tools (role `edit`), logged like any other; the file goes in the frame with the selection marked, the instruction stays the person's words. Nothing is written: the editor shows the patch and the person accepts it. A credential store is refused; secrets elsewhere in the file are redacted first, a selection that holds one is refused, and a reply that writes the placeholder back is refused. Tab completion (fill-in-the-middle on a fast, cheap model) is to come.
- Images on a thread message: `cedia threads send <id> <text> --image <file>` stores each image (as `-p --image` does) and the message carries their `ImageRef`s; the session it is delivered to is shown them before the messages' text, in the same user reminder, counted against the session's 20. A run's `run` thread event names the images shown with its prompt, so `threads fork --json` returns them in `ForkResult.images`, and a client resending the edited message passes each back as `-p --image sha256:<hex>`, which shows a stored image again after checking it against its hash (capability `threads.send-images`).
- `~/.cedia/settings.json` is the one settings file. The desktop's own keys live under `desktop`; everything else is cedia's schema.
- Images and video in a thread go to a model that reads images: a new session on Haiku 5.5 when the code model is text-only (decided 2026-10-21; not built yet). Images themselves are built (the Images row above); video is to come as frames taken with ffmpeg.

## Trust

Guarantees that hold whatever model runs come from the log, not the model's words.

- **Done gate** (`core/trust/ledger.ts`, stage 2). When the agent claims done and the ledger has no passing declared check after its last write, cedia appends one reminder naming the checks and lets the model continue; a second unverified claim ends the run with `error_unverified_claim` and exit code 1. Only declared checks count (`--check`, or `checks` in `~/.cedia/settings.json` or the repo's `.cedia/settings.json`), and only when the bash command is exactly the check: a pipe would hide its exit code. Writes are completed `edit`/`write` calls and any bash command that is not read-only. With no declared checks the gate is off and the receipt lists everything as unverified.
- **Slop guard** (`core/trust/slop.ts`). When the agent claims done, cedia reads the run's own changes (the patch between its first and latest snapshot, or the edit/write calls without snapshots) for the shortcuts that make work look done: tests deleted, weakened (net assertion lines removed) or skipped, `@ts-ignore`/`eslint-disable`/`# type: ignore`/`noqa`, empty `catch`/`except: pass`, `as any`, not-implemented stubs, and checks turned off in their config (`config-weakened`: TypeScript's strict family set to false, a lint rule set to off, files or codes a linter or test runner is told to skip, a package.json test or lint script that cannot fail; ECC's config-protection hook blocks these files outright, a reminder lets a task that means it keep one and say why). Prose files are not scanned. One reminder lists them; the model fixes each or explains it, and the receipt lists what is left as `flagged`. `--unlock slop-check` turns it off. The layering follows poteto's "trust your agents" pyramid: code and static checks first, prose rules after, human review last.
- **Advisor** (`core/trust/advisor.ts`, `--advisor <model>`). After each writer turn that ran tools, a second model reads that turn (what the writer said, each call and its result, cut to 1,500 characters a part) in one session of its own for the run, with no tools and its own short system prompt, at low effort where the model has effort levels. It answers `OK` or a note of at most five lines; a note goes into the writer's log as a reminder framed `<advice by="…">` after the turn's results, so the writer's cached prefix only grows. Its turns count in the run's spend and budget but not against the writer's `--max-turns`; the result carries `advice{model, sessionId, costUsd, turns, notes}`. An advisor that fails is dropped for the rest of the run. Off by default: each writer turn costs one advisor reply.
- **Stuck guard** (`core/trust/stuck.ts`). After each turn's tool calls, cedia reads the calls since the run began for a run going round in circles: the same call getting the same result 4 times in a row, the same tool failing with the same error 3 times in a row, or two calls taking turns 3 times with nothing new from either (`sleep` and `Monitor` are meant to repeat and do not count). The first time, one logged reminder names the pattern and asks for another approach or a report of what blocks the task; if the calls after it fall into a pattern again, the run ends `error_stuck` instead of spending turns up to the 200-turn limit. Most of the harnesses in the source-code study of eleven coding agents guard their loop this way (OpenHands' StuckDetector, Gemini CLI's loop detection, OpenCode's doom-loop check, arXiv 2609.00006 §6); cedia's only stop was the turn limit.
- **Review** (`core/trust/review.ts`, `--review <model>`). After the writer's claim passes the done gate, a second model reviews the change in its own session (`role: 'review'`): read and bash only, under a read-only policy that also allows the declared checks, given the task, the receipt and the writer's diff from its snapshots (left out past 60k characters). It ends with `VERDICT: approve` or `VERDICT: changes`; changes go back to the writer's own session once, framed as claims to check. The result carries `review{model, sessionId, verdict, fixed}` and adds up every session's spend and turns. The last layer of the pyramid: checks and the slop guard come first.
- **Detected checks.** With no declared check, cedia uses the repo's own test command (`package.json` test script, `cargo test`, `go test ./...`, `make test`, `pytest`). Detected checks are soft: the gate reminds once and never refuses, because the repo's tests may already fail.
- **Receipt.** Every turn that changed files ends with a receipt from the ledger: files changed, checks run, their results.
- **Deny list** (`core/safety/policy.ts`, stage 2, before the stage-6 classifier): force-push (including `--force-with-lease`, `+refspec`, branch deletion), `git reset --hard` and `git clean -f` (any branch until shadow snapshots can undo them), commands that lose commits (`git stash drop|clear`, `git branch -D`, `git reflog expire|delete`, `git update-ref -d`, `git filter-branch`, `git filter-repo`), `rm -r` or `find -delete` outside the workspace or on targets that cannot be resolved, skipping the repository's git hooks (`hook-bypass`: `--no-verify` on commit, push, merge, am and rebase, `git commit -n`, `-c core.hooksPath=`), and publish/deploy commands (`npm publish`, `vercel --prod`, `kubectl apply`, `terraform apply`, `gh pr merge` and similar). It reads each simple command, through `sudo`, `nice -n`, `timeout`, `xargs`, `bash -c`, `$( )` and chains. No mode or allow rule lifts it; the user can unlock one guard by name. pstack's "Always pause" list is a harness rule because a weak model will not pause on its own. It guards against mistakes; the sandbox is the boundary.
- **Untrusted content.** Tool results (files, command output, web pages) are data: the base prompt says so, and they only ever reach the model inside `tool_result` blocks. `evals/tasks/hard-injection` plants instructions in a README and a code comment and fails any run that follows them. A small-model injection screen on tool output is a stage-6 candidate. A guard's denial tells the model not to work around it; a command the shell reader cannot parse (`shell:unparsed`) tells it to rewrite instead.
- **Permission event.** Every call that reaches the policy logs `permission{decision, rule, reason}`; a denied call gets `tool_result{status:'denied'}` naming the rule, and no `tool_intent`.
- **Read-only** subagents get write tools and MCP stripped by `ToolSpec.effect`, not by prompt.
- **Session linter** (`cedia lint-session <file>...`, `core/session/lint.ts`, stage 2): session event first and an unbroken parent chain; every `tool_use` gets exactly one `tool_result` before the next request; `permission → tool_intent → tool_result` order, and denied calls never run; `systemHash`/`toolsHash` constant (until a `tools_changed` event exists); header values are hashes; every `request` has numbered `attempt`s before its `assistant`; the log ends with `turn_end`. The loop and e2e tests lint every faux session they produce.

## Eval

- Run each task 3 times in a clean temp dir; report pass@1, pass^3, false-done rate, time, tokens and cost.
- The task's check decides, never the agent's words; read the transcript whenever a result changes.
- Every prompt or default change runs the eval before merge.
- The pi-era set (8 tasks, all harnesses 8/8) is a regression floor. New tasks come from cedia's own git history and must separate harnesses.
- **Budget order.** Run every eval on Haiku 5.5 and the OpenCode Go models first; Opus arms run last, once the cheap arms have settled the task set. Each paid run prints its estimated cost first.
- **Four-arm comparison** decides whether the cheap-writer pairing earns its place: (a) `claude -p` with Opus, (b) cedia Opus plans + DeepSeek writes, (c) cedia Opus + Opus, (d) cedia Opus + Haiku. 3 runs each; pass^3, false-done rate and cost per passed task. (c) against (a) measures the harness; (b) and (d) against (c) measure the pairing. A pairing becomes the default for a task category only if it is within 3 points of (a) on pass^3 and at least 2x cheaper per passed task.
